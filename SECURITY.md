# Security policy

## Threat surface

This project has a deliberately small surface. It has no server, no database,
no user accounts, no telemetry and no runtime network access. The published
site is static and makes no external requests. Every input is a committed CSV
fixture generated by committed code.

The realistic risks are therefore:

1. A malicious pull request that introduces code executed by CI.
2. A dependency compromise reaching the workflow.
3. A change that makes the test suite pass while the underlying numbers are
   wrong. This is treated as a security issue, not merely a bug, because the
   entire value of the repository is the trustworthiness of a green run.

## Mitigations in place

- Every GitHub Actions step is pinned to a commit SHA, not a moving tag.
- The default workflow token is limited to `contents: read`. Only the deploy
  job is granted `pages: write` and `id-token: write`.
- Python dependencies are pinned by exact version.
- Pull requests from forks run without secrets, and none are required.
- A mutation test asserts that every compared value is load bearing, so a
  change that quietly disables comparison fails before it merges.

## Reporting a vulnerability

Open a GitHub issue for anything that does not require confidentiality. For
something that does, use the repository's private vulnerability reporting form
under the Security tab. Please include the commit SHA and, if possible, a
failing reproduction.

There is no bounty. There is a commitment to fix, to state what happened in the
commit message, and to record any resulting change of convention in
`docs/divergences.md`.

## Out of scope

Findings that depend on running untrusted input through the reference kernel
locally, and reports about the absence of features this project has explicitly
declined to build, such as authentication or telemetry.
